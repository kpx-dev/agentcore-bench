# AgentCore Runtime V2: six questions, measured

These answers come from `us-west-2` on 2026-10-27, using the probe agent and the experiments in
this directory. The full evidence (tables, per-session data, CloudTrail, usage records) is in:
- [`runs/20261027T191511Z-r1027191511/FINDINGS.md`](runs/20261027T191511Z-r1027191511/FINDINGS.md), the main run: 5 runtimes, 10 sessions per runtime for cold starts;
- [`runs/20261027T201545Z-pricing1/FINDINGS.md`](runs/20261027T201545Z-pricing1/FINDINGS.md), a follow-up for the env-var cap and V1 metering.

| # | Question | Measured answer |
|---|---|---|
| 1 | Is V2 supported in VPC mode, and does VPC change restore/start time? | **Supported, and cold starts are not slower. Creating the runtime is much slower.** A V2 runtime in a private-only VPC (no internet; S3 gateway endpoint plus ECR and Logs interface endpoints; isolation checked from inside the session) served 10/10 new sessions. Cold-invoke p50 was **1.79 s in VPC vs 2.07 s in PUBLIC** (p90 2.16 vs 2.42 s). Create → READY took **9.4 min in VPC vs 3.3 min in PUBLIC**. Later updates of the VPC runtime took 3.4 min. For reference, V1 took 4.5 min (VPC) vs 18 s (PUBLIC). |
| 2 | Does V2 keep pre-started/restored instances, or restore every new session on demand? | **On demand; V2 keeps no pool.** All 20 new V2 sessions were restored from the version's snapshot 0.00–0.09 s before their first request arrived. Nothing was booted or restored ahead of time, including a 3-minute zero-traffic window after READY. **V1 does keep a pool**, which is why V1 instances start before any session arrives. Each runtime pre-booted at least 10 microVMs at create, let each run ~3.3 s, paused it, and resumed one ~0.13 s before a session's first request (instances up to ~13 min old). At this low, sequential load, V1's pool hits (p50 0.55–0.63 s) were faster than V2 restores (p50 1.8–2.1 s). |
| 3 | Can a runtime created on V2 be switched back to V1? | **Yes; the platform version is not fixed at create.** `UpdateAgentRuntime(platformVersion=V1)` created a new version and reached READY in **6 s**, and `GetAgentRuntime` then reported V1. Switching back to V2 took **3.1 min** (a snapshot build). A session opened before the switches kept its instance through both. An endpoint pinned to an older V2 version kept serving snapshot restores while DEFAULT ran V1. The first V1 sessions after the switch were fresh boots (cold p50 3.4 s) until the warm pool refilled. |
| 4 | If an update points at the same image tag, does AgentCore re-pull and rebuild the snapshot? | **Yes.** After the tag moved to a new build, an update with the configuration unchanged resolved the tag again (CloudTrail: `BatchGetImage` by tag, then by the new digest). It built a new snapshot (3.1 min PUBLIC, 3.4 min VPC), and new sessions ran the new build. **An update with nothing changed at all also creates a new version and rebuilds the snapshot** (3.1–3.4 min). With no update, new sessions kept restoring the old build. |
| 5 | Is the snapshot per runtime version, and does each endpoint restore from the version it points to? | **Each endpoint restores the version it points to, but the snapshot is per endpoint and version, not per version.** Every endpoint create or update ran its own ~3.1-minute snapshot build, even for a version another endpoint already had. CloudTrail shows `snapstart-build-DEFAULT`, `snapstart-build-LIVE` and `snapstart-build-test` sessions, and each endpoint restored its own build. **Because each build re-resolves the version's image tag, one version can run different images on different endpoints.** `test`, created on version 1 after the tag had moved, ran build B, while DEFAULT and LIVE on version 1 ran build A. |
| 6 | Is there a charge for snapshot creation, storage or restore? | **No separate charge for any of the three. Restore time is billed, though, as the start of the session.** The [pricing page](https://aws.amazon.com/bedrock/agentcore/pricing/) never mentions snapshots. microVMs bill only "the CPU and memory consumed by your agent session", for a session that "spans from microVM ready, initialization, active processing, idle periods, until session termination". The only storage items are the image's ECR storage (or S3 for code zips) and managed session storage. Measured: all 179 per-second usage records belong to sessions the PoC opened, and none fall in the 5 snapshot builds (15.7 min of building). Each session's first metered second, the restore, showed **~1.5 GB and ~2 vCPU**, then ~1.3 GB; ≈ $0.0002 for a one-call session, of which ~13 s was metered after the last reply despite `StopRuntimeSession`. V2's own rates are higher: $0.1276/vCPU-h and $0.0169/GB-h, vs $0.0895 and $0.00945 on V1 (+43% / +79%). |

## Also measured

- **The V2 env-var cap is 2,560 bytes, enforced after the API call succeeds.** `CreateAgentRuntime` accepted 3,000 bytes, then the runtime went `CREATE_FAILED` 6 s later: "payload is 3004 bytes, exceeding the 2560-byte maximum supported for V2 agents". Over 4,000 bytes is rejected synchronously. A pipeline has to poll the status to see the failure.
- **Startup code does not run "once per version".** Every snapshot build booted the agent twice (two snapshot copies) and test-restored each copy once. Every endpoint build repeats this. Sessions share whatever startup created: a `uuid4()` drawn at import took only 2 distinct values across 10 sessions. Every session reports hostname `localhost` and PID 1.
- **V2 create/update timing.** The image is pulled and the agent boots ~90 s after the API call. The agent is healthy 1.6 s after boot, but the snapshot is taken ~70 s later, and READY follows ~35 s after that, once each copy has been test-restored. So expect ~3.1–3.4 min per V2 create, update or endpoint change, and ~9.4 min for a first VPC create. CI/CD timeouts of ~180 s fail.
- **The first file read after a restore is slow.** A full read of a 32 MiB file baked into the image took 3–5 ms on V1 and **2.0–8.7 s on V2**. In the VPC runtime, later sessions read it in ~40 ms, probably a host-side cache. The page cache is not part of the snapshot.
- **Inbound auth held.** An unsigned `InvokeAgentRuntime` was refused with HTTP 403.
